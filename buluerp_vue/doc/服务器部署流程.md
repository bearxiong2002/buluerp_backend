## 2. 本地构建（Windows PowerShell）

在项目根目录执行。前端是嵌套的独立 Git 仓库，需要同时检查两边变更；不要覆盖其他人的未提交修改。

```powershell
Set-Location D:\workspace\java\buluerp_backend\buluerp_vue
git status --short
git -C buluErp_Frontend status --short

# 每次发布使用新的编号。后续 SSH 步骤沿用这个值。
$releaseId = 'release-' + (Get-Date -Format 'yyyyMMdd-HHmmss')
$releaseDir = Join-Path 'ruoyi-admin/target/releases' $releaseId

# 包含测试。依赖已缓存时可加 -o；首次构建不要使用离线模式。
mvn package
if ($LASTEXITCODE -ne 0) { throw '后端构建失败，停止部署' }

Push-Location buluErp_Frontend/buluerp_front
# 缺少依赖时先执行 npm ci；已有依赖时无需每次重装。
npm run build-only
$frontBuildExit = $LASTEXITCODE
Pop-Location
if ($frontBuildExit -ne 0) { throw '前端构建失败，停止部署' }

New-Item -ItemType Directory -Path $releaseDir -Force | Out-Null
Copy-Item ruoyi-admin/target/ruoyi-admin.jar "$releaseDir/backend-upload.jar"
tar -czf "$releaseDir/frontend.tar.gz" -C buluErp_Frontend/buluerp_front/dist .
if ($LASTEXITCODE -ne 0) { throw '前端打包失败' }
Get-FileHash "$releaseDir/backend-upload.jar", "$releaseDir/frontend.tar.gz" -Algorithm SHA256
Write-Output "本次发布编号：$releaseId"
```

`npm run build-only` 验证 Vite 构建，不等于完整 TypeScript 类型检查。2026-09-06 构建成功，但存在其他页面 Element Plus 类型导入及大 chunk 警告；判断成功应以退出码为准。

## 4. 准备生产包

从服务器当前正式 JAR 读取 `application-prod.yml`，放入新 JAR，保留线上数据库及上传目录配置。配置只在内存中处理，不打印密码。若此次明确需要修改生产配置，应先单独核对差异，再调整此步骤。

```bash
python3 - <<'PY'
import os
import zipfile
from pathlib import Path

stage = Path(os.environ['stage'])
key = 'BOOT-INF/classes/application-prod.yml'
with zipfile.ZipFile('/opt/buluerp/backend/ruoyi-admin.jar') as current:
    production_config = current.read(key)
assert production_config
with zipfile.ZipFile(str(stage / 'backend-upload.jar')) as source:
    assert key in source.namelist()
    with zipfile.ZipFile(str(stage / 'ruoyi-admin.jar'), 'w') as output:
        for entry in source.infolist():
            output.writestr(entry, production_config if entry.filename == key else source.read(entry.filename))
print('生产配置已保留')
PY

sha256sum "$stage/ruoyi-admin.jar" > "$backup/new-backend.sha256"
mkdir "$stage/frontend"
tar -xzf "$stage/frontend.tar.gz" -C "$stage/frontend"
test -s "$stage/frontend/index.html"
# 保留旧的哈希资源文件，降低已打开页面加载旧 chunk 失败的概率。
cp -an /www/wwwroot/buluerp_front/assets/. "$stage/frontend/assets/"
chmod -R a+rX "$stage/frontend"

nginx -t
grep -E 'proxy_(read|send)_timeout' /etc/nginx/conf.d/buluerp_front.conf
```

生产 Nginx 当前已经是 600 秒，不要再次运行只匹配 `300s` 的一次性替换命令。前端 `vite.config.ts` 里的代理配置只影响本地开发，生产环境由 Nginx 负责。若确需调整站点配置，修改后必须先 `nginx -t`，通过后再 reload。

## 5. 切换版本

确认当前没有需要等待结束的导入操作，再进行切换。此步骤会短暂中断后端请求。下列命令依赖前面设置的 `stage`、`backup`；若 SSH 重新连接，先重新设置这些变量。

```bash
cp -a "$stage/ruoyi-admin.jar" /opt/buluerp/backend/ruoyi-admin.jar.new
systemctl stop buluerp-backend
mv /opt/buluerp/backend/ruoyi-admin.jar.new /opt/buluerp/backend/ruoyi-admin.jar
systemctl start buluerp-backend
```

2026-09-06 实测后端约 38 秒启动。启动期间短暂 `Connection refused` 正常；应等待接口恢复，不能只看到 systemd 的 `active` 就认为验收完成。

```bash
healthy=0
for i in $(seq 1 60); do
  if curl -fsS --max-time 3 http://127.0.0.1:8080/captchaImage 2>/dev/null |
     python3 -c 'import json,sys; sys.exit(0 if json.load(sys.stdin).get("code") == 200 else 1)' 2>/dev/null; then
    healthy=1
    break
  fi
  sleep 2
done

if [ "$healthy" != 1 ]; then
  echo '后端健康检查失败：停止切换前端，按第 7 节回滚'
  exit 1
fi

mv /www/wwwroot/buluerp_front "$stage/frontend-previous"
mv "$stage/frontend" /www/wwwroot/buluerp_front
if command -v restorecon >/dev/null 2>&1; then
  restorecon -R /www/wwwroot/buluerp_front
fi
nginx -t
systemctl reload nginx
```

切换或验证中途失败时按第 7 节回滚；不要反复覆盖部署文件。以上为手动流程，不承诺任意步骤失败后自动回滚。

## 7. 回滚

重新 SSH 登录后，指定需要恢复的备份编号。先确认三个备份文件均存在；这套回滚只恢复程序与站点配置，不恢复数据库。

```bash
set -eu
releaseId='release-YYYYMMDD-HHMMSS'
backup="/opt/buluerp/backups/$releaseId"
failed="/opt/buluerp/deploy_uploads/rollback-$(date +%Y%m%d-%H%M%S)"
test -s "$backup/ruoyi-admin.jar"
test -s "$backup/frontend/index.html"
test -s "$backup/buluerp_front.conf"
mkdir "$failed"

systemctl stop buluerp-backend
cp -a /opt/buluerp/backend/ruoyi-admin.jar "$failed/ruoyi-admin.jar"
cp -a /etc/nginx/conf.d/buluerp_front.conf "$failed/buluerp_front.conf"
cp -a "$backup/ruoyi-admin.jar" /opt/buluerp/backend/ruoyi-admin.jar
cp -a "$backup/buluerp_front.conf" /etc/nginx/conf.d/buluerp_front.conf
cp -a "$backup/frontend" "$failed/frontend-restored"
if [ -e /www/wwwroot/buluerp_front ]; then
  mv /www/wwwroot/buluerp_front "$failed/frontend-failed"
fi
mv "$failed/frontend-restored" /www/wwwroot/buluerp_front
if command -v restorecon >/dev/null 2>&1; then
  restorecon -R /www/wwwroot/buluerp_front
fi
nginx -t
systemctl start buluerp-backend
systemctl reload nginx
```

回滚后重新执行健康检查及页面验证，保留失败版本供排查。

## 8. 已知问题与复用注意事项

- `ClientAbortException / ClosedChannelException` 表示返回响应时客户端或代理连接已关闭，不等同于数据库导入的原始错误。需结合此前的行级错误及请求线程、时间判断，避免把旧请求和新请求混在一起。
- 布产导入前端等待上限为 10 分钟，Nginx 对应超时为 600 秒。代码已增加缺失模具物料的批量预检查及错误日志。缺失基础资料仍需修正，不会因部署自动补齐。
- 本地 `X6015` 模板曾在 Excel 第 166 行引用不存在的 `A1082-1`；这是当时检查结果，不应据此自动修改生产数据。
- 后端日志末尾有 Swagger 参数类型警告时，以实际启动结果和接口结果为准。
- 不要调用 `/www/server/nginx/sbin/nginx`；当前实际使用的是 `/usr/sbin/nginx`。
- `ruoyi-admin/target/deploy-tools/deploy.py` 是 2026-09-06 的临时脚本，`target` 目录可能被清理，且脚本写死发布编号、旧的 300 秒配置前提。**不要直接复用该脚本；以本文的参数化步骤为准。**
- Python/Paramiko 自动化如需读取凭据，应从环境变量或交互输入获取；输出设置 UTF-8，避免 Windows GBK 无法打印启动日志中的特殊字符。
- 后续部署只需核对服务、固定路径及配置是否仍存在。只有这些信息发生变化时，才重新探查并更新本文。
